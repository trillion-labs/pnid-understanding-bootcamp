# P&ID 에이전트의 답을 평가하는 방법

> P&ID 에이전트는 도면번호만 맞히면 끝나는 검색기가 아닙니다. 올바른 원본을 선택하고, 질문의 핵심 단서를 실제 이미지에서 확인하고, 확인하지 못한 내용을 추측하지 않아야 합니다.

앞 단원에서는 Claude Code와 Codex에 같은 업무 계약을 전달했습니다. 이제 어떤 결과를 더 좋은 결과라고 판단할지 기준을 정하겠습니다.

## 평가할 작업을 먼저 구분합니다

여러 P&ID 가운데 관련 시트를 고르는 `도면 검색 작업`과, 선택된 한 장에서 장비와 연결을 읽는 `단일 도면 이해 작업`은 서로 다른 기준으로 평가해야 합니다.

도면 검색 작업에서는 올바른 도면번호를 골랐는지가 중요합니다. 단일 도면 이해 작업에서는 장비 태그, 위·아래 연결, 설비 요소 해석과 확인 보류가 중요합니다.

## 도면번호 정답만으로는 왜 부족한가요?

기존 Feeder #C 관련 도면 찾기 실행 가운데 일부는 `J-11520-ZM-105-005`를 올바르게 선택했습니다. 그러나 판단 근거에서 `11520-E-MT-18`을 Expansion Joint 태그라고 잘못 설명했습니다.

즉, 최종 도면번호는 맞았지만 설비 요소 수준의 설명은 틀렸습니다.

도면번호 exact match만 채점하면 이 오류를 발견할 수 없습니다. 따라서 결과를 여러 층으로 나누어 평가해야 합니다.

## 네 가지 평가 영역

### 1. 도면 선택(Retrieval): 올바른 도면을 찾았나요?

- 기대한 drawing ID를 선택했습니까?
- 가장 관련 있는 도면 하나를 요구했는데 불필요한 후보를 여러 개 제시하지 않았습니까?
- Revision과 시트를 올바르게 확인했습니까?

### 2. 근거(Evidence): 판단 근거가 맞나요?

- 질문의 핵심 장비명과 태그를 이미지에서 직접 확인했습니까?
- 근거 위치를 부분 확대 이미지나 위치 상자로 남겼습니까?
- Motor와 joint처럼 가까운 설비 요소를 구분했습니까?
- 파일명이나 OCR 결과만으로 설비 요소의 존재를 확정하지 않았습니까?

### 3. 에이전트 행동: 모르는 내용을 어떻게 처리했나요?

- 현재 이미지로 읽을 수 없는 태그를 추측하지 않았습니까?
- 확인한 사실과 해석을 분리했습니까?
- 추가 자료가 필요한 이유를 설명했습니까?
- 검토 상태를 남겼습니까?

### 4. 효율: 어느 정도 자원을 사용했나요?

- 실행 시간은 얼마나 걸렸습니까?
- Tool call과 turn 수는 몇 회입니까?
- Input, cached input, output token은 얼마입니까?
- API 등가 비용 또는 CLI 보고 비용은 얼마입니까?

효율은 품질 점수에 바로 더하지 않습니다. 품질 기준을 통과한 결과끼리 비교합니다. 빠르게 틀린 답을 만드는 것은 개선이 아니기 때문입니다.

## 처음에는 세 가지 검토 상태만 사용합니다

각 근거 행을 다음 세 상태로 나눌 수 있습니다.

| 상태 | 의미 | 다음 행동 |
|---|---|---|
| 확인됨 | 글자, 심벌과 위치를 원본에서 확인했습니다. | 결과를 유지합니다. |
| 수정 필요 | 대상은 있지만 글자·위치·설비 요소 해석이 틀렸습니다. | 원래 값과 수정값을 함께 기록합니다. |
| 확인하지 못함 | 현재 이미지와 자료로 확정할 수 없습니다. | 값을 채우지 않고 추가 자료를 요청합니다. |

`AI가 그렇게 말했습니다`는 원본 근거가 아닙니다. 검토자는 같은 이미지 위치에서 글자와 심벌을 다시 확인합니다.

## Feeder #C 관련 도면 찾기 질문을 위한 10점 평가표

| 영역 | 평가 항목 | 점수 |
|---|---|---:|
| 도면 선택 | `J-11520-ZM-105-005`를 선택했습니다. | 2 |
| 도면 선택 | 불필요한 추가 drawing ID가 없습니다. | 1 |
| 근거 | `VIBRO FEEDER #C`와 `11520-M-VB-03C`를 확인했습니다. | 2 |
| 근거 | 근거 확대 이미지 또는 위치 상자를 제공했습니다. | 2 |
| 근거 | Motor와 joint 근거를 혼동하지 않았습니다. | 1 |
| 에이전트 행동 | 확인하지 못한 내용을 추측하지 않았습니다. | 1 |
| 에이전트 행동 | 원본 파일과 검토 상태를 명시했습니다. | 1 |

총점은 10점입니다.

점수가 높다고 실제 운전·정비 판단을 자동화할 수 있다는 뜻은 아닙니다. 이 점수는 관련 도면을 찾고 근거를 설명하는 학습 task에 대한 평가입니다.

## 기준 답안은 어떻게 만드나요?

에이전트 결과를 채점하려면 먼저 사람이 원본을 검토하여 만든 기준 답안이 필요합니다. 평가 분야에서는 이를 `gold answer` 또는 `gold data`라고도 부릅니다.

좋은 기준 답안에는 도면번호만 들어 있지 않습니다.

- 질문 원문
- 기대 drawing ID와 revision
- 반드시 확인할 query term
- 혼동하면 안 되는 설비 요소
- 허용할 수 있는 근거 위치
- 현재 자료로 unresolved여도 되는 내용
- 검토자와 기준 답안 버전

기준 데이터는 `data/benchmark-cases.jsonl`에 있습니다. 기술 파일 안에서는 기존 결과와 연결하기 위해 질문 ID를 유지합니다.

기준 데이터도 영구적으로 완벽한 정답은 아닙니다. 검토 중 오류를 발견하면 수정 이유를 기록하고 버전을 올립니다.

## 단일 도면 이해 실험을 위한 4점 평가표

앞 단원의 단일 도면 이해 실행은 다음 네 항목으로 검토했습니다.

1. Feeder #C와 장비 태그를 정확히 읽었습니까?
2. 바로 위쪽 Reception Bin 2 연결을 확인했습니까?
3. 아래쪽 선에서 직접 보이는 내용과 흐름 방향 해석을 구분했습니까?
4. Motor와 Expansion Joint 근거를 구분했습니까?

| 모델 | 전체+짧은 질문 | 부분 확대+짧은 질문 | 부분 확대+근거 확인 질문 |
|---|---:|---:|---:|
| Claude Sonnet | 3/4 | 3/4 | 3/4 |
| Codex Luna | 4/4 | 3/4 | 3/4 |
| Codex Terra | 3/4 | 2/4 | 3/4 |

부분 확대 이미지는 작은 글자를 읽는 데 도움이 되었지만 연결 방향 해석 오류를 만들었습니다. 근거 확인 순서는 motor와 joint 구분을 도왔지만 태그 오독과 아래쪽 연결 해석을 모든 모델에서 해결하지는 못했습니다.

## 오류를 유형으로 기록합니다

점수만 기록하면 다음에 무엇을 바꿔야 할지 알기 어렵습니다. 오류 원인을 다음처럼 분류할 수 있습니다.

| 오류 유형 | 예시 | 다음에 검토할 것 |
|---|---|---|
| 문서 선택 오류 | 2/5나 3/5를 선택했습니다. | 후보 검색과 전체 이미지 요약을 검토합니다. |
| 글자 판독 오류 | VB를 VF로 읽었습니다. | 이미지 해상도와 부분 확대를 검토합니다. |
| 문맥 오류 | Off-page reference를 현재 도면번호로 사용했습니다. | 전체 이미지 재검증을 추가합니다. |
| 설비 요소 해석 오류 | E-MT를 Expansion Joint 태그로 사용했습니다. | 범례와 의미 검토 지침을 개선합니다. |
| 근거 누락 | 도면번호만 답하고 위치를 남기지 않았습니다. | 출력 형식에 근거 위치를 추가합니다. |
| 과신 오류 | 보이지 않는 Ash Leak 감지기를 만들었습니다. | 확인하지 못함 상태와 검토 기준을 추가합니다. |
| 과정 오류 | 어떤 파일과 이미지를 보았는지 기록하지 않았습니다. | Run log와 trace를 저장합니다. |

## 위치 상자 평가는 언제 사용하나요?

객체 탐지 데이터셋을 만들 때에는 AI가 찾은 위치 상자와 사람이 만든 기준 상자가 얼마나 겹치는지 계산할 수 있습니다.

이 값을 `Intersection over Union`, 줄여서 IoU라고 부릅니다.

```text
IoU = 두 상자가 겹친 면적 / 두 상자를 합친 전체 면적
```

IoU가 1이면 두 상자가 같습니다. 0이면 전혀 겹치지 않습니다.

그러나 Q005처럼 여러 근거를 함께 보여 주는 넓은 근거 구역은 IoU만으로 평가하기 어렵습니다. 필요한 질문 단서가 상자 안에 포함되었는지, 검토 문맥이 충분한지를 함께 봐야 합니다.

## 여러 결과를 비교할 때 사용하는 지표

객체 탐지나 태그 추출 task가 많아지면 다음 지표를 사용할 수 있습니다.

- Precision은 AI가 찾았다고 한 항목 가운데 실제로 맞은 비율입니다.
- Recall은 실제 정답 가운데 AI가 찾아낸 비율입니다.
- F1은 Precision과 Recall을 함께 반영한 값입니다.

처음부터 공식을 외우기보다 의미를 이해하는 것이 중요합니다.

AI가 없는 장비를 많이 만들면 Precision이 낮아집니다. 실제 장비를 많이 놓치면 Recall이 낮아집니다.

## 비용과 품질을 함께 보는 방법

두 run의 품질 점수가 같다면 더 적은 시간과 token을 사용한 run이 효율적입니다.

반면 token이 30% 줄었지만 근거 점수가 4점에서 1점으로 떨어졌다면 개선이라고 보기 어렵습니다.

그래서 결과표에는 다음 값을 함께 기록합니다.

```text
Quality score
Critical component error count
Duration
Tool calls
Input/cached/output tokens
Cost basis
```

`Cost basis`에는 Claude CLI 보고 비용인지, OpenAI API 단가를 사용한 등가 추정치인지 적습니다.

## 다음 단원으로 넘어갑니다

이제 에이전트의 오류가 어디에서 발생했는지 알 수 있습니다. 다음 단계는 점수가 낮았다는 사실을 보고 프롬프트를 무작정 길게 만드는 것이 아닙니다.

데이터 준비, 이미지 입력, 프롬프트, 도구, 스킬, 모델 가운데 어떤 원인이 가장 유력한지 먼저 분류합니다. 그중 하나만 바꾸고 같은 질문을 새 세션에서 다시 실행합니다.

이 과정을 개선 Loop라고 부릅니다. 개선 Loop 단원에서는 Feeder #C 관련 결과를 이용하여 개선 전후를 비교하겠습니다.
