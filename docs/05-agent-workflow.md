# Claude Code와 Codex에게 도면 작업을 맡기는 방법

> AI 에이전트에게 일을 맡긴다는 것은 질문 한 문장을 잘 쓰는 것만을 의미하지 않습니다. 어떤 파일을 읽고, 어떤 도구를 사용하고, 무엇을 결과로 남기며, 언제 작업이 끝났다고 판단할지를 함께 정하는 것입니다.

앞 단원에서는 Feeder #C 관련 결과를 같은 열을 가진 표로 정리했습니다. 이제 Claude Code와 Codex가 원본 파일을 확인하고, 필요한 이미지를 선택하고, 표를 작성하고, 스스로 검사하도록 업무를 맡겨보겠습니다.

## 일반 대화와 에이전트 작업은 무엇이 다른가요?

일반 대화에서는 사용자가 이미지를 첨부하고 질문하면 AI가 답변을 작성합니다.

에이전트 작업에서는 AI가 작업 폴더 안의 파일을 읽고, PDF 정보를 조사하고, 필요한 부분을 확대하고, 결과 파일을 저장하고, 검증 명령을 실행할 수 있습니다.

쉽게 비유하면 일반 대화는 회의 중 질문에 답하는 동료와 비슷합니다. 에이전트는 작업 폴더와 완료 조건을 전달받고 실제 산출물을 만드는 작업자와 비슷합니다.

## 작업을 맡길 때 필요한 다섯 가지

에이전트에게 다음 다섯 가지를 알려 주면 작업을 검토하기 쉬워집니다.

### 1. 목표

무엇을 완료해야 하는지 설명합니다.

```text
이 P&ID에서 Vibro Feeder #C의 장비 태그, 바로 위쪽 장비, 아래쪽 출구 연결과 Expansion Joint 관련 근거를 확인해 주세요.
```

### 2. 입력

어떤 파일을 사용할 수 있는지 설명합니다.

```text
원본 PDF는 source/sample-pid.pdf입니다.
전체 이미지는 assets/overview/sample-pid-overview-1600.png이고,
Feeder #C 주변 확대 이미지는 `assets/regions/feeder-c-area.png`입니다.
```

### 3. 판단 규칙

어떤 근거를 사용하고, 무엇을 추측하지 않아야 하는지 설명합니다.

```text
파일명은 후보를 찾는 데만 사용하고 설비 요소가 존재한다는 증거로 사용하지 마세요.
이미지에서 읽은 문자열과 설비 요소 해석을 구분해 주세요.
확인하지 못한 내용은 unresolved로 남겨 주세요.
```

### 4. 출력 형식

어떤 결과를 어디에 남길지 설명합니다.

```text
query_term, observed_text_or_symbol, inferred_component,
evidence_region, status, note 열을 가진 표로 작성해 주세요.
```

### 5. 완료 조건

어떤 검사를 통과해야 끝나는지 설명합니다.

```text
VIBRO FEEDER #C와 11520-M-VB-03C를 각각 확인하고,
motor와 joint 근거를 혼동하지 않았는지 검토한 뒤 완료해 주세요.
```

## Feeder #C 단일 도면 이해 작업을 맡기는 요청

다섯 요소를 하나의 요청으로 합치면 다음과 같습니다.

```text
source/sample-pid.pdf와 준비된 전체 구조용 이미지·Feeder #C 주변 확대 이미지를 사용하여
이 P&ID에서 Vibro Feeder #C의 주변 연결을 확인해 주세요.

Feeder #C 주변 확대 이미지에서 VIBRO FEEDER #C, 11520-M-VB-03C,
outlet joint 문맥을 각각 확인해 주세요.

이미지에서 직접 읽은 내용과 설비 요소 해석을 구분하고,
E-MT/EM motor 근거를 Expansion Joint 태그로 사용하지 마세요.
확인하지 못한 내용은 unresolved로 남겨 주세요.

결과는 질문 단서별 근거 표와 확인한 연결 관계 요약으로 작성해 주세요.
마지막에는 각 근거를 원본 이미지에서 다시 확인해 주세요.
```

이 요청은 길어 보일 수 있지만 새로운 지식을 많이 넣은 것은 아닙니다. Feeder #C 주변 연결을 검토할 때 사람이 사용하는 기준을 업무 계약으로 정리했습니다.

## 에이전트는 어떤 순서로 작업하나요?

에이전트 작업은 다음 순환으로 이해할 수 있습니다.

```text
현재 상태를 확인합니다.
        ↓
작업 계획을 세웁니다.
        ↓
파일을 읽고 도구를 사용합니다.
        ↓
결과를 검사합니다.
        ↓
확인한 내용과 남은 문제를 기록합니다.
```

이를 영어로는 `Observe → Plan → Act → Check → Record`라고 표현하기도 합니다.

각 단계를 별도 문장으로 출력하게 만드는 것이 목표는 아닙니다. 작업 결과를 보았을 때 이 과정이 실제로 수행되었는지 확인할 수 있으면 됩니다.

## Coarse-to-fine을 에이전트가 선택하게 하려면

스킬이나 프로젝트 지침에 `항상 네 조각으로 분할하세요`라고 적으면 불필요한 작업이 늘어날 수 있습니다.

대신 다음과 같이 판단 기준을 제공합니다.

```text
전체 이미지에서 질문의 작은 구분자를 읽기 어렵다면 관련 구역을 확대하세요.
부분 확대 이미지를 사용한 경우에는 최종 판단 전에 전체 이미지의 제목과 계통 문맥을 다시 확인하세요.
```

이 지침은 확대가 필요한 상황과 확대 후 잃을 수 있는 문맥을 함께 설명합니다.

## P&ID 스킬은 무엇을 저장하나요?

이 프로젝트에는 `skills/pid-visual-evidence/` 스킬이 있습니다.

스킬은 특정 도면의 정답을 외우는 파일이 아닙니다. 여러 P&ID 질문에서 반복되는 판단 기준을 저장합니다.

- 파일명과 카탈로그는 후보를 좁히는 자료입니다.
- 작은 글자는 필요한 구역을 확대해서 확인합니다.
- 이미지에서 본 문자열과 설비 요소 해석을 구분합니다.
- 도면번호 정답과 근거 정답을 따로 평가합니다.
- 확인하지 못한 질문 단서를 숨기지 않습니다.

스킬을 사용한 결과가 실제로 좋아졌는지는 반드시 같은 질문으로 전후 비교해야 합니다.

## Claude Code와 Codex에 같은 일을 맡길 때

두 제품의 내부 동작 방식과 사용 가능한 도구는 다를 수 있습니다. 내부 reasoning 방식을 같게 만들려고 하기보다 외부 업무 계약을 같게 맞춥니다.

다음 항목을 동일하게 유지합니다.

- 현업 질문
- 사용할 원본 데이터
- 출력 열과 상태 값
- 근거 요구사항
- 검토 기준
- 새 세션 여부

다음 항목은 제품별로 기록합니다.

- 정확한 모델 이름
- 추론 강도 설정
- 사용할 수 있었던 도구
- 스킬을 불러온 방식
- 입력·캐시·출력 token과 비용 보고 방식

## 에이전트가 멈추고 질문해야 하는 경우

에이전트가 모든 빈칸을 스스로 채우도록 요구하면 근거 없는 값이 생길 수 있습니다. 다음 상황에서는 사람에게 확인을 요청하거나 unresolved로 남기는 것이 적절합니다.

- 필요한 관련 시트가 제공되지 않았습니다.
- 같은 태그가 두 가지로 읽힙니다.
- 부분 확대 이미지의 경계 밖으로 연결선이 이어집니다.
- 범례만으로 설비 요소의 의미를 확정할 수 없습니다.
- 실제 운전·정비·안전 판단으로 질문 범위가 확장됩니다.
- 기존 원본이나 검토 완료 데이터를 덮어써야 합니다.

## 작업 기록은 왜 남기나요?

최종 답변만 보존하면 다음 실행에서 무엇이 달라졌는지 알기 어렵습니다. 최소한 다음 항목을 기록합니다.

```text
Run ID
사용한 질문과 모델
입력 이미지와 데이터 버전
스킬 또는 지침 버전
선택한 도면번호
확인한 근거와 확인하지 못한 단서
실행 시간, 도구 호출 수, token과 비용
Raw response와 trace 경로
```

이 기록은 다음 단원의 평가 세트 데이터가 됩니다. 평가 분야에서는 이를 `benchmark`라고도 부릅니다.

## 직접 점검해 봅니다

다음 두 요청을 비교해 보세요.

요청 A:

```text
이 도면을 다 분석해서 표로 만들어 주세요.
```

요청 B:

```text
이 P&ID에서 Feeder #C, 장비 태그, outlet joint 문맥을 확인하고,
각 질문 단서의 원본 위치와 확인 상태를 표로 작성해 주세요.
Motor와 joint 근거를 구분하고 확인하지 못한 단서를 남겨 주세요.
```

요청 A가 나쁜 프롬프트라는 뜻은 아닙니다. 도면을 자유롭게 탐색하거나 에이전트가 먼저 계획을 제안하게 할 때 사용할 수 있습니다.

요청 B는 결과를 같은 평가 기준으로 비교하려는 상황에 더 적합합니다. 성공 기준과 출력 형식이 정해져 있기 때문입니다.

## 다음 단원으로 넘어갑니다

이제 Claude Code와 Codex가 같은 업무 계약을 가지고 실행할 수 있습니다. 다음에는 결과를 어떻게 평가할지 정해야 합니다.

도면번호만 맞혔는지, 근거까지 맞혔는지, 확인하지 못한 내용을 정직하게 남겼는지, 비용이 얼마나 들었는지를 나누어 측정하겠습니다. 이 평가 기준이 있어야 프롬프트나 스킬을 수정한 뒤 실제로 좋아졌다고 말할 수 있습니다.
