# 평가 결과를 이용하여 에이전트를 개선하는 방법

> 에이전트 개선은 프롬프트를 계속 길게 만드는 작업이 아닙니다. 실제 질문에서 발생한 오류를 분류하고, 데이터·도구·지침·모델 가운데 하나만 변경한 뒤, 같은 조건으로 다시 평가하는 과정입니다.

앞 단원에서는 Feeder #C 관련 결과를 도면 선택, 판단 근거, 에이전트 행동과 효율로 나누어 평가했습니다. 이제 그 평가 결과를 이용하여 무엇을 바꿀지 결정해 보겠습니다.

## 같은 질문과 기준으로 반복 평가하는 이유

에이전트가 한 번 좋은 답을 만들었다고 해서 항상 잘 작동한다고 말할 수는 없습니다. 반대로 한 번 틀렸다고 해서 모델 전체가 부족하다고 말할 수도 없습니다.

평가 세트(benchmark)는 실제 업무를 대표하는 질문 묶음과 같은 채점 기준을 사용하여 여러 실행을 비교하는 시험판입니다.

이 워크북에서는 다음 두 현업 질문으로 시작합니다.

### Feeder #C 관련 도면 찾기 질문

> Bottom Ash Vibro Feeder #C Outlet Expansion Joint Ash Leak과 관련된 P&ID를 찾아 주세요.

이 질문은 작은 장비 태그와 motor/joint 의미 구분을 확인합니다.

### Q008

> Reception Bin 2에서 OFA Line으로 연결되는 Flexible Hose의 Pinhole 및 Ash Leak과 관련된 P&ID를 찾아 주세요.

이 질문은 같은 Feeder #C 주변 확대 이미지에서 Flexible Hose, Reception Bin 2와 Boiler OFA 문맥을 확인합니다. 프로젝트 데이터에서는 이 구역을 R03이라고 부릅니다.

두 질문은 같은 도면을 정답으로 사용하지만 필요한 시각 근거가 다릅니다. 하나의 도면을 외운 스킬이 아니라, 질문에 맞는 근거를 찾는 능력을 평가할 수 있습니다.

## 좋은 Benchmark 질문은 어떤 특징이 있나요?

실제 업무에서 사람들이 묻는 질문을 사용해야 합니다. 파일명에 정답이 그대로 들어 있는 질문만 모으면 실제 도면 이해 능력을 평가하기 어렵습니다.

질문 세트에는 다음 차이가 포함되어야 합니다.

- 쉬운 질문과 어려운 질문
- 장비명으로 찾는 질문과 태그로 찾는 질문
- 한 시트 안에서 답을 찾는 질문과 여러 시트를 비교해야 하는 질문
- 작은 글자를 읽어야 하는 질문
- 연결 관계를 따라가야 하는 질문
- 현재 자료만으로 확인할 수 없는 질문

현재 Q005와 Q008은 최소한의 시작 세트입니다. 실제 benchmark로 확장하려면 다른 계통과 다른 drawing family를 추가해야 합니다.

## 기준 답안에는 무엇이 들어가야 하나요?

도면번호만 저장하면 설비 요소 수준의 오류를 채점할 수 없습니다.

Feeder #C 관련 도면 찾기 기준 답안에는 다음 내용이 들어 있습니다.

- 기대 도면: `J-11520-ZM-105-005`, Rev.F
- 확인할 장비명: `VIBRO FEEDER #C`
- 확인할 태그: `11520-M-VB-03C`
- 확인할 문맥: Feeder outlet 아래쪽 joint 심벌 후보
- 금지할 혼동: `11520-E-MT-18`을 Expansion Joint 태그로 사용하지 않습니다.
- 근거 구역: Feeder #C 주변의 파란 상자
- 허용할 확인하지 못함 상태: Expansion Joint의 고유 태그는 현재 이미지에서 확인하지 못할 수 있습니다.

이 데이터는 `data/benchmark-cases.jsonl`에 저장되어 있습니다.

## 개선 Loop의 전체 흐름

```text
같은 질문을 실행합니다.
        ↓
결과를 같은 기준으로 채점합니다.
        ↓
가장 중요한 오류 하나를 선택합니다.
        ↓
오류가 발생한 원인을 분류합니다.
        ↓
한 가지 요소만 변경합니다.
        ↓
새 세션에서 같은 질문을 다시 실행합니다.
        ↓
품질과 비용을 비교하여 변경을 유지하거나 되돌립니다.
```

## 1단계: 가장 중요한 오류를 고릅니다

모든 오류를 한 번에 고치려고 하지 않습니다. 현업 결과에 가장 큰 영향을 주는 오류를 하나 선택합니다.

실제 Feeder #C 관련 실행에서는 다음 오류가 있었습니다.

- Luna는 전체 이미지에서 VB를 VF로 잘못 읽었습니다.
- Sonnet은 crop을 별도의 Coal Handling 계통이라고 잘못 판단했습니다.
- Luna와 Terra는 crop의 off-page reference를 현재 도면번호로 사용했습니다.

예를 들어 motor와 joint 혼동을 이번 iteration의 목표 오류로 선택할 수 있습니다.

## 2단계: 오류 원인을 분류합니다

오류의 원인이 다르면 개선 방법도 달라집니다.

| 원인 | 나타나는 현상 | 검토할 개선 |
|---|---|---|
| 데이터 준비 | 작은 태그를 읽지 못합니다. | 더 선명한 crop이나 OCR 후보를 준비합니다. |
| 전체 문맥 부족 | Crop을 다른 계통으로 오해합니다. | 전체 이미지 재검증 단계를 추가합니다. |
| 후보 검색 부족 | 1/5~5/5 가운데 잘못된 시트를 고릅니다. | 제목과 drawing catalog를 사용합니다. |
| Agent 지침 부족 | Motor와 joint 근거를 섞습니다. | 관찰과 설비 요소 해석을 분리합니다. |
| 출력 구조 부족 | 근거 위치와 확인하지 못한 단서가 없습니다. | 근거 열과 상태 값을 추가합니다. |
| 평가 기준 부족 | 도면번호만 맞으면 통과합니다. | 설비 요소 근거 점수를 추가합니다. |
| 모델 한계 | 선명한 crop과 지침이 있어도 오독합니다. | 다른 모델·effort 또는 사람 검토를 사용합니다. |

일부 오류는 이미지와 지침을 개선해도 남을 수 있습니다. 이 경우에는 다른 모델이나 사람 검토를 비교하여 모델 한계인지 확인해야 합니다.

## 3단계: 한 번에 하나만 바꿉니다

다음처럼 여러 요소를 동시에 바꾸면 무엇이 효과를 만들었는지 알 수 없습니다.

```text
모델을 바꿉니다.
이미지를 새로 자릅니다.
OCR을 추가합니다.
프롬프트를 길게 바꿉니다.
스킬도 함께 추가합니다.
```

대신 iteration을 나눕니다.

```text
Iteration 0: 원본 PDF와 짧은 질문을 사용합니다.
Iteration 1: Drawing catalog만 추가합니다.
Iteration 2: 전체 구조용 이미지와 부분 확대 도구만 추가합니다.
Iteration 3: P&ID 근거 검토 스킬만 추가합니다.
Iteration 4: 실제 설비 요소 오류를 교정하는 규칙 한 줄만 수정합니다.
```

각 iteration은 새 세션에서 실행합니다. 이전 대화 내용이 남아 있으면 변경 효과와 대화 기억 효과가 섞이기 때문입니다.

품질 점수가 같거나 높아졌는지 먼저 확인합니다. 그다음 비용과 시간을 비교합니다.

## 5단계: 변경을 유지할지 결정합니다

다음 질문에 모두 답합니다.

- 목표로 삼은 오류가 줄었습니까?
- 기존에 맞던 질문이 나빠지지 않았습니까?
- 다른 질문에서도 같은 개선이 유지됩니까?
- 근거가 더 명확해졌습니까?
- 추가 비용이 품질 향상으로 정당화됩니까?
- 특정 정답을 프롬프트에 하드코딩한 것은 아닙니까?

Q005에서만 좋아지고 Q008이나 다른 계통 질문에서 나빠진 규칙은 일반 스킬에 바로 넣지 않습니다.

## 실제 기존 결과에서 볼 수 있는 개선 사례

GS Agent의 기존 Codex Luna Feeder #C 질문 실행을 비교하면 다음과 같습니다.

- Raw baseline은 올바른 도면을 찾았지만 tool call이 26회였습니다.
- Catalog만 제공한 run은 3/5 도면을 선택하여 실패했습니다.
- Overview와 crop을 제공한 run은 올바른 5/5를 선택했고 tool call은 12회였습니다.

이 결과는 catalog만 추가한다고 개선되지 않는다는 점을 보여 줍니다. 실제 component를 볼 수 있는 시각 도구가 필요했습니다.

하지만 올바른 도면을 찾은 뒤에도 joint 근거는 사람이 다시 검토해야 했습니다. 따라서 도면 선택 개선과 근거 개선을 분리해야 합니다.

## Claude Code와 Codex를 공정하게 비교합니다

다음 조건은 같게 유지합니다.

- 현업 질문 원문
- 원본 도면과 이미지 버전
- 스킬과 지침 버전
- 새 세션
- 출력 형식
- 기준 답안 version
- 검토자와 평가표

다음 항목은 제품별 차이로 기록합니다.

- 모델 이름과 effort
- 사용할 수 있는 도구
- 스킬을 불러온 방식
- CLI가 보고하는 usage 형식
- 캐시 사용량

두 제품의 답변 문체가 비슷한지를 평가하지 않습니다. 같은 현업 질문에 대해 올바른 도면과 검토 가능한 근거를 만들었는지 평가합니다.

## 직접 개선 Loop를 작성해 봅니다

다음 빈칸을 채워보세요.

```text
가장 중요한 오류:

오류 원인 분류:

이번 iteration에서 바꿀 한 가지:

바꾸지 않고 유지할 조건:

Before 결과 경로:

After 결과 경로:

변경을 유지할지 여부와 이유:
```

실행 기록은 `experiments/improvement-loop/iteration-log.csv`에 저장할 수 있습니다.

## 스킬 개선으로 이어지는 경우

같은 오류가 여러 질문과 모델에서 반복된다면 스킬에 일반적인 판단 규칙을 추가할 수 있습니다.

예를 들어 다음 규칙은 특정 질문의 정답을 직접 알려 주지 않습니다.

```text
이미지에서 본 문자열과 설비 요소 해석을 분리합니다.
E-MT/EM처럼 motor 근거로 보이는 표기를 nearby joint의 태그로 자동 사용하지 않습니다.
```

반면 `Q005의 정답은 J-11520-ZM-105-005입니다`라는 문장은 평가 정답을 스킬에 유출하므로 사용할 수 없습니다.

## 워크북의 한 Loop를 마칩니다

이제 다음 과정을 모두 경험했습니다.

1. P&ID와 현업 질문을 이해했습니다.
2. 전체 이미지와 crop을 실제 모델에 실행했습니다.
3. 답의 근거 위치를 기록했습니다.
4. 결과를 구조화된 표로 만들었습니다.
5. Drawing과 Evidence를 분리하여 평가했습니다.
6. 오류 원인을 분류했습니다.
7. 한 가지를 바꾸고 같은 조건으로 다시 평가하는 방법을 배웠습니다.

이 과정은 P&ID에만 적용되는 특별한 요령이 아닙니다. 큰 문서, 복잡한 이미지, 여러 도구를 다루는 AI 에이전트를 개선할 때에도 같은 원칙을 사용할 수 있습니다.
