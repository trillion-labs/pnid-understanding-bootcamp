# 평가 결과로 에이전트 개선하기

> 에이전트를 개선하려면 틀린 항목을 정확히 찾고 원인을 분류해야 합니다. 한 가지 요소만 변경한 뒤 같은 정답으로 다시 평가합니다.

앞 단원에서는 Reception Bin 태그, V186, Feeder 태그, 전동기 태그에 각각 1점을 매겼습니다. 이번에는 그 결과를 보고 무엇을 바꿀지 결정합니다.

## 같은 질문과 정답을 유지하는 이유

변경 전후에는 같은 질문과 정답을 사용해야 점수 차이의 원인을 개선 요소로 좁힐 수 있습니다.

이 워크북에서는 다음 조건을 고정합니다.

- 원본 도면: `J-11520-ZM-105-005`, Rev.F
- 질문: Reception Bin 2의 A측 출구에서 Feeder #C 전동기까지 네 값 확인
- 기준 답안: `11520-M-SI-04`, `V186`, `11520-M-VB-03C`, `EM / 11520-E-MT-18`
- 모델과 추론 설정
- 새 세션 사용
- 4점 평가표

변경할 항목만 하나 선택합니다.

## 개선 과정의 전체 흐름

```text
같은 질문을 실행합니다.
        ↓
네 항목을 같은 기준으로 채점합니다.
        ↓
가장 중요한 오류 하나를 선택합니다.
        ↓
오류 원인을 분류합니다.
        ↓
이미지·데이터·프롬프트·스킬 중 하나만 바꿉니다.
        ↓
새 세션에서 같은 질문을 다시 실행합니다.
        ↓
점수, 오류 상태와 비용을 비교합니다.
```

## 1단계: 가장 중요한 오류를 고릅니다

실제 전체 이미지 실행에서는 다음 오류가 있었습니다.

- Sonnet은 Feeder #C 전동기를 `M-TP16`으로 잘못 읽었습니다.
- Luna는 Feeder 태그를 `11520-M-V-03C`, 전동기를 `EX / 11520-M-E-17`로 잘못 읽었습니다.
- Terra는 Feeder와 전동기 태그를 확인하지 못했다고 남겼습니다.

세 결과는 모두 작은 Feeder와 전동기 표기에서 문제를 보였습니다. 첫 번째 개선 목표를 `Feeder와 전동기 태그 판독`으로 정하겠습니다.

## 2단계: 오류 원인을 분류합니다

| 원인 | 나타나는 현상 | 검토할 개선 |
|---|---|---|
| 이미지 해상도 부족 | 작은 태그를 다른 문자열로 읽거나 보류합니다. | 질문 구역을 더 크게 제공합니다. |
| 이미지 범위 부족 | 정답에 필요한 장비가 이미지 밖에 있습니다. | Bin부터 전동기까지 한 화면에 포함합니다. |
| 인접 태그 혼동 | 오른쪽 Feeder의 `03B`나 `E-MT-19`가 섞입니다. | 장비와 태그의 위치 관계를 확인하게 합니다. |
| 출력 구조 부족 | 네 항목 가운데 빠진 값이 보이지 않습니다. | 항목별 표를 사용합니다. |
| 모델 한계 | 선명한 이미지에서도 같은 문자를 반복해서 틀립니다. | 다른 모델 또는 사람 검토를 비교합니다. |

원인을 먼저 정해야 프롬프트를 고칠지, 이미지를 바꿀지 판단할 수 있습니다.

## 3단계: 한 번에 하나만 바꿉니다

첫 번째 비교에서는 질문을 유지하고 이미지만 바꿉니다.

```text
변경 전: 1600px 전체 이미지 + 짧은 질문
변경 후: Feeder #C 주변 확대 이미지 + 같은 짧은 질문
```

그 결과는 다음과 같았습니다.

| 모델 | 변경 전 | 변경 후 | 차이 |
|---|---:|---:|---:|
| Claude Sonnet | 3/4 | 4/4 | +1 |
| Codex Luna | 2/4 | 4/4 | +2 |
| Codex Terra | 2/4 | 4/4 | +2 |

세 모델 모두 개선되었습니다. 확대 이미지에는 네 정답과 연결 관계가 모두 포함되어 있었고 작은 글자가 충분히 크게 보였습니다.

## 4단계: 프롬프트 변경은 별도로 평가합니다

다음 비교에서는 이미지를 유지하고 질문만 바꿉니다.

```text
변경 전: Feeder #C 주변 확대 이미지 + 짧은 질문
변경 후: 같은 이미지 + 단계별 확인 질문
```

| 모델 | 짧은 질문 | 단계별 질문 | 차이 |
|---|---:|---:|---:|
| Claude Sonnet | 4/4 | 4/4 | 0 |
| Codex Luna | 4/4 | 4/4 | 0 |
| Codex Terra | 4/4 | 3/4 | -1 |

단계별 질문은 점수를 높이지 않았고 Terra에는 인접 태그 혼동을 만들었습니다. 이번 질문에서는 짧은 질문을 기본값으로 유지하는 편이 타당합니다.

이 결과는 `프롬프트가 자세할수록 좋다`는 가정이 항상 맞지 않음을 보여 줍니다.

## 6단계: 변경을 유지할지 결정합니다

다음 질문에 답합니다.

- 목표로 삼은 오류가 줄었습니까?
- 기존에 맞던 항목이 나빠지지 않았습니까?
- 같은 조건을 반복해도 결과가 유지됩니까?
- 근거 위치가 더 명확해졌습니까?
- 추가 비용이 품질 향상으로 정당화됩니까?
- 기준 답안 자체를 프롬프트에 알려 준 것은 아닙니까?

이번 한 번의 실행에서는 부분 확대 이미지는 유지할 가치가 있었습니다. 반면 단계별 질문은 추가 점수를 만들지 않았으므로 기본 프롬프트에 바로 넣을 근거가 부족했습니다.

## Claude Code와 Codex를 공정하게 비교합니다

다음 조건은 같게 유지합니다.

- 질문 원문
- 원본 이미지와 부분 확대 이미지 버전
- 새 세션
- 출력 형식
- 네 항목의 기준 답안
- 검토자와 평가표

제품별 차이는 별도로 기록합니다.

- 모델 이름과 추론 설정
- 사용할 수 있는 도구
- 입력·캐시·출력 token 보고 방식
- CLI가 보고한 비용과 API 등가 추정 비용

답변 문체나 길이가 아니라 네 문자열과 연결 관계가 정확한지 평가합니다.

## 스킬 개선으로 이어지는 경우

같은 오류가 여러 모델이나 반복 실행에서 나타나면 일반적인 판단 규칙을 스킬에 추가할 수 있습니다.

예를 들어 다음 규칙은 특정 정답을 알려 주지 않습니다.

```text
대상 장비에 직접 연결된 태그를 확인합니다.
인접 장비의 태그를 현재 장비의 값으로 사용하지 않습니다.
```

반면 `Feeder #C의 전동기 태그는 11520-E-MT-18입니다`처럼 기준 답안을 스킬에 넣으면 평가 정답이 유출됩니다. 이런 규칙은 사용할 수 없습니다.

## 직접 개선 과정을 작성해 봅니다

```text
가장 중요한 오류:

오류 원인:

이번에 바꿀 한 가지:

바꾸지 않고 유지할 조건:

변경 전 점수와 오류 상태:

변경 후 점수와 오류 상태:

변경을 유지할지 여부와 이유:
```

이로써 P&ID 한 장을 읽고, 답을 원본 위치와 연결하고, 네 개의 명확한 정답으로 평가한 뒤 한 가지를 바꿔 다시 평가하는 과정을 마쳤습니다.
