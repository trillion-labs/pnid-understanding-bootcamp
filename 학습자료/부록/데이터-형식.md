# AI의 답을 검색하고 비교할 수 있는 데이터로 바꾸는 방법

> 앞 단원에서는 P&ID 한 장 자체의 기본정보, 큰 구역과 주요 태그를 JSON으로 정리했습니다. 이번 단원에서는 구조화의 대상을 AI 답변으로 바꿉니다.

구조화 데이터는 AI가 문장으로 설명한 기존 정보를 같은 종류의 칸에 나눠 담습니다. 이렇게 정리하면 결과를 검색·비교·검토하거나 다시 처리하기 쉽습니다.

앞 단원에서는 위치 상자를 이용하여 AI의 답을 원본 위치와 연결했습니다. 이제 `무엇을 보았는지`, `어떻게 해석했는지`, `어디에서 보았는지`, `검토가 끝났는지`를 같은 형식으로 기록해 보겠습니다.

## 자연어 답변만으로는 무엇이 어려운가요?

AI가 다음과 같이 답했다고 가정해 보겠습니다.

> Reception Bin 2의 태그는 11520-M-SI-04입니다. A측 하부 출구에서 V186을 거쳐 Vibro Feeder #C로 연결됩니다. Feeder 태그는 11520-M-VB-03C이고 전동기는 EM / 11520-E-MT-18입니다.

사람이 한 번 읽기에는 충분히 좋은 답입니다. 하지만 이런 답을 Claude와 Codex에서 여러 조건으로 반복 생성하면 다음 질문에 답하기 어려워집니다.

- 어떤 모델이 Feeder 태그를 맞혔습니까?
- V186을 정확히 읽지 못한 실행은 무엇입니까?
- Feeder #C의 전동기를 오른쪽의 `11520-E-MT-19`와 혼동한 실행은 무엇입니까?
- 아직 사람이 검토하지 않은 결과는 무엇입니까?
- 같은 위치를 다시 확대하려면 어떤 좌표를 사용해야 합니까?
- 다음 revision에서 장비 태그가 바뀌었습니까?

자연어 문장은 표현 방식이 자유롭습니다. 같은 뜻을 서로 다른 말로 쓸 수 있기 때문에 컴퓨터가 자동으로 비교하기 어렵습니다.

## 구조화 데이터는 주소록과 비슷합니다

다음 메모를 생각해 보세요.

> 김민수 님은 A사에서 일하고 전화번호는 010-1234-5678입니다.

이 내용을 주소록에 넣으면 다음과 같이 나뉩니다.

| 이름 | 회사 | 전화번호 |
|---|---|---|
| 김민수 | A사 | 010-1234-5678 |

원래 문장의 각 부분에 열 이름을 붙였습니다. 정보의 내용은 그대로지만 회사별로 묶거나 전화번호가 없는 행을 쉽게 찾을 수 있습니다.

P&ID 결과도 같은 방식으로 정리할 수 있습니다.

## Feeder #C 단일 도면 이해 답변을 표로 바꾸어 봅니다

앞의 자연어 답변을 질문의 단서별로 나누면 다음과 같습니다.

| 질문 ID | 확인할 단서 | 이미지에서 본 근거 | 해석한 설비 요소 | 위치 | 상태 |
|---|---|---|---|---|---|
| Feeder-C-Read | Reception Bin 2 태그 | 11520-M-SI-04 | equipment_tag | 파란 근거 구역 | 확인됨 |
| Feeder-C-Read | A측 밸브 | V186 | valve | 파란 근거 구역 | 확인됨 |
| Feeder-C-Read | Feeder #C 태그 | 11520-M-VB-03C | equipment_tag | 파란 근거 구역 | 확인됨 |
| Feeder-C-Read | Feeder #C 전동기 | EM / 11520-E-MT-18 | motor | 파란 근거 구역 | 확인됨 |

이 표를 보면 AI가 무엇을 확인했고 무엇을 보류했는지 한눈에 알 수 있습니다.

`이미지에서 본 근거`와 `해석한 설비 요소`를 분리한 이유도 중요합니다. `11520-E-MT-18`이라는 문자열을 읽는 것과, 그 문자열이 Feeder #C의 전동기를 뜻한다고 연결하는 것은 서로 다른 작업입니다. 기술 데이터에서는 설비 요소를 `component`라고 기록합니다.

## 어떤 상황에서 구조화 데이터가 도움이 되나요?

### 여러 모델의 결과를 비교합니다

Claude는 `확인할 수 없습니다`라고 쓰고 Codex는 `unknown`이라고 쓸 수 있습니다. 자연어만 비교하면 다른 결과처럼 보입니다. 상태 열을 `확인됨`, `검토 필요`, `확인하지 못함`으로 통일하면 같은 기준으로 비교할 수 있습니다.

### 빠진 값을 자동으로 찾을 수 있습니다

모든 결과에 질문 ID, 도면번호, 근거 위치와 검토 상태가 있는지 자동으로 검사할 수 있습니다.

### 다음 에이전트 작업에 다시 사용합니다

`검토 필요`인 행만 골라 더 높은 해상도로 다시 확인하도록 요청할 수 있습니다. 저장된 위치 좌표를 이용하여 같은 구역의 부분 확대 이미지를 다시 만들 수도 있습니다.

### Revision을 비교합니다

도면이 Rev.F에서 Rev.G로 바뀌었을 때 장비 태그나 연결 관계가 달라진 후보를 찾기 쉬워집니다.

### 평가 세트를 만들 수 있습니다

사람이 검토하여 만든 기준 데이터와 에이전트 결과가 같은 열을 사용하면 누락, 잘못 읽은 태그, 잘못된 설비 요소 의미와 근거 위치를 행 단위로 비교할 수 있습니다.

## 모든 답을 구조화해야 하나요?

답의 사용 목적에 따라 형식을 고릅니다. `이 도면의 큰 구조를 자유롭게 설명해 주세요`처럼 한 번 읽고 끝나는 탐색형 질문에는 자연어가 더 편합니다.

다음과 같은 경우에 구조화가 필요해집니다.

- 결과를 나중에 다시 검색합니다.
- Claude와 Codex 결과를 비교합니다.
- 같은 도면을 여러 모델과 입력 조건에서 반복합니다.
- 사람의 검토 상태를 남깁니다.
- 같은 위치를 다시 처리합니다.
- 성능을 수치로 평가합니다.

즉, 구조화 데이터는 모든 대화를 딱딱하게 만드는 규칙이 아니라 반복 가능한 업무를 만들기 위한 도구입니다.

## 처음에는 표 한 행이면 충분합니다

처음에는 JSON 문법보다 아래 순서에 따라 필요한 구조부터 익히면 됩니다.

```text
AI의 자연어 답변
        ↓
사람이 읽기 쉬운 표
        ↓
열 이름과 허용할 상태를 합의합니다.
        ↓
반복 처리를 위해 CSV 또는 JSONL로 저장합니다.
```

워크북의 핵심 실습에서는 Markdown 표를 사용합니다. CSV와 JSONL은 결과가 많아졌을 때 사용합니다.

## 어떤 열을 사용해야 하나요?

Feeder #C 단일 도면 이해 작업에는 다음 열부터 시작할 수 있습니다.

| 열 | 의미 | 예시 |
|---|---|---|
| query_id | 현업 질문 식별자입니다. | Feeder-C-Read |
| drawing_id | 분석한 도면번호입니다. | J-11520-ZM-105-005 |
| query_term | 질문에서 확인할 단서입니다. | VIBRO FEEDER #C |
| observed_text_or_symbol | 이미지에서 직접 읽은 내용입니다. | 11520-M-VB-03C |
| inferred_component | 근거를 이용하여 해석한 설비 요소입니다. | vibro_feeder |
| evidence_region | 원본에서 다시 확인할 위치입니다. | 파란 근거 구역 |
| status | 현재 확인 상태입니다. | confirmed |
| note | 제한사항이나 검토 이유입니다. | 오른쪽 E-MT-19는 제외함 |

열은 실제로 검색하거나 검토할 정보만큼만 만듭니다.

## 상태 값은 왜 제한하나요?

자유롭게 `아마 맞는 것 같습니다`, `조금 애매합니다`, `잘 모르겠습니다`라고 쓰면 모델마다 표현이 달라집니다.

처음에는 다음 세 상태만 사용해도 충분합니다.

- `confirmed`: 이미지에서 직접 확인했습니다.
- `needs_review`: 후보는 있지만 사람이 더 확인해야 합니다.
- `unresolved`: 현재 자료로 확인하지 못했습니다. 데이터 파일에서는 이 영문 값을 사용합니다.

근거가 부족할 때는 `확인하지 못함(unresolved)`으로 기록합니다. 값을 추측해 채우는 것보다 정확하고 안전한 결과입니다.

## 판독 확신도와 검토 상태는 어떻게 다른가요?

판독 확신도(`confidence`)는 현재 이미지에서 글자나 심벌이 얼마나 선명하게 보이는지를 표현합니다.

`review_status`는 다른 사람이 결과를 검토했는지를 표현합니다.

confidence가 high여도 두 번째 검토자가 아직 보지 않았다면 `needs_second_review`일 수 있습니다. 두 필드는 서로 다른 질문에 답합니다.

## 도면 데이터를 더 깊게 만들 때 사용하는 네 층

이 표보다 더 큰 데이터셋을 만들 때에는 정보를 다음 네 층으로 나눌 수 있습니다.

```text
Document → Region → Object → Relation
```

### Document

원본 파일과 revision, 페이지, 이미지 크기와 checksum을 기록합니다.

### Region

도면에서 분석할 구역과 부분 확대 위치를 기록합니다.

### Object

장비, 계기, 밸브와 태그의 위치와 속성을 기록합니다.

### Relation

어떤 장비가 다른 장비에 연결되는지, 어떤 계기가 어느 장비에 부착되는지 기록합니다.

네 층을 한꺼번에 만들기보다 필요한 범위에서 시작하세요. 태그 문자열만 비교한다면 Document와 Region이면 충분합니다. Bin, 밸브, Feeder와 전동기의 연결 관계까지 저장하려면 Object와 Relation을 확장합니다.

## JSONL 예시를 읽어봅니다

표의 한 행을 JSON 객체로 쓰면 다음과 같습니다.

```json
{
  "query_id": "Feeder-C-Read",
  "drawing_id": "J-11520-ZM-105-005",
  "query_term": "VIBRO FEEDER #C",
  "observed_text_or_symbol": "VIBRO FEEDER #C / 11520-M-VB-03C",
  "inferred_component": "vibro_feeder",
  "evidence_region": {
    "image": "실습자료/이미지/feeder-c-원본-확대.png",
    "bbox": [220, 1030, 750, 1550]
  },
  "status": "confirmed",
  "note": "E-MT-19 belongs to the neighboring feeder and is excluded"
}
```

JSONL은 이런 JSON 객체를 한 줄에 하나씩 저장한 파일입니다. 행 단위로 추가하고 오류를 찾기 쉬워 에이전트 실행 결과를 모을 때 유용합니다.

저장소의 `data/document.json`, `data/regions.jsonl`, `data/objects.example.jsonl`에서 Document, Region과 Object의 실제 예시를 확인할 수 있습니다.

## 자동으로 확인할 수 있는 것과 사람이 확인해야 하는 것

컴퓨터는 다음 항목을 빠르게 검사할 수 있습니다.

- 모든 행에 query_id가 있습니까?
- 상태 값이 허용된 값입니까?
- 위치 좌표가 이미지 경계를 벗어나지 않았습니까?
- 참조한 이미지 파일이 실제로 존재합니까?
- ID가 중복되지 않았습니까?

반면 다음 항목은 원본 도면을 보고 판단해야 합니다.

- 글자를 올바르게 읽었습니까?
- 심벌 의미를 범례와 맞게 해석했습니까?
- Feeder #C의 전동기를 오른쪽 Feeder의 전동기와 혼동하지 않았습니까?
- 부분 확대 이미지에서 잘린 연결을 임의로 이어 붙이지 않았습니까?
- 확인하지 못한 값을 그럴듯하게 채우지 않았습니까?

구조화 데이터는 의미 검토를 자동화하기보다 검토할 대상을 빠르게 찾도록 돕습니다.

| A-side valve |  |  | 파란 근거 구역 |  |  |
